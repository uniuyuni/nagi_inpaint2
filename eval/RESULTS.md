## WTA (勝者総取り) 学習 — **不採用**
### 第1版 StageFW (出力層のみ K 分岐)
仮説がほぼ同一。**神託選択が first 選択を下回った** (PSNR 21.29 vs 21.43) = 多様性なし。
人物val: grain 0.320 / lpips 0.0059 / psnr 21.20 → L1 モデルと完全に同一。
原因: K 個のヘッドがバックボーン全体を共有し、同じ特徴の線形読み出ししか表現できない。

学習中の検証が `grain 1.021` を報告したが人物マスクでは 0.098 だった。
原因は**細いマスクで grain_ratio が `nan` になり、validate() が非有限値を黙って捨てていた**こと。
→ R11/R12 を導入 (eval/quickval.py, tests/test_metrics_sanity.py)。

### 第2版 StageFW2 (デコーダを K 分岐 + 枝ごとの埋め込み + 相対摂動)
多様性の問題は**解決した**: 神託-first の PSNR 差 -0.14 → **+2.4〜+3.3 dB**。
事前学習重みからの初期化で仮説間差が 4.4e-8 (実質ゼロ) だった問題も、
枝の重みへの相対摂動 (_BRANCH_PERTURB=0.08) で 5.7e-3 に改善 (10万倍)。

**しかしぼけは直らなかった** (quickval, 人物マスク):
| step | grain | lpips |
|---|---|---|
| 1500 | 0.3521 | 0.00587 |
| 2500 | 0.3140 | 0.00573 |
| 3500 | 0.3316 | 0.00602 |
grain は 0.29〜0.35 を振動 (基準 0.322)、lpips はむしろ悪化。step 3500 で打ち切り。

**結論: 多様性と鮮鋭度は別物。** WTA は「K個の仮説の間で平均しない」ことは保証するが、
**各仮説は自分が勝つケース集合の中で依然 L1 で学習される**ため、その集合が多峰的なら
やはり平均を出してぼける。勝率も [0.08 0.15 0.71 0.06] と1ヘッドに集中し、
実質そのヘッドが従来通り全体を L1 学習しているのに近い状態だった。

## 盲検A/B (人間判定) — **全敗**
人物val 20ケース、左右無作為、手法名・数値の表示なし。判定はユーザ本人。
```
我々の勝ち 0  負け 16  同等 4
勝率 0.0%  95%CI [0.0, 19.4]%  両側二項検定 p = 0.00003
```
**指標が大幅に過小評価していた。** 知覚距離では 0.0059 対 0.0052 (13%劣位) で
「接近」と報告していたが、人間の判断では一度も選ばれなかった。
簡易 LPIPS はこの用途の品質を代表しない。**盲検A/Bを主判定に据える。**

ユーザによる敗因の内訳:
- **ほとんどのケースでぼけた塊が見える** (Stage F の平均値回帰)
- **ところどころ四角い継ぎ目** (32px ブロックコピーの格子)
- **「同等」の4件は「両方良い」ではなく「両方悪い」** —
  片方はディティールがおかしく、片方はぼけている。LaMa もそこでは失敗している

→ Stage G の目標を「知覚距離で上回る」から**「盲検で過半数を取る」**に置き換える。
→ 穴の内部を生成で埋めれば、ぼけと格子の両方が同時に消える
   (内部でコピーを使わなくなるため)。細いマスクのコピーは +2.28 dB で維持。

## Stage G (残差 Rectified Flow) — **撤退**
G0 (前提の測定) は通過: 残差は白色雑音でない (自己相関 lag1 +0.911、PSD 低域/高域比 175倍)、
Stage B の検索パッチと相関 +0.210 (対照 +0.009)、穴の奥ほど残差が大きい (0.044 -> 0.126)。

G1 第1版 (3,000 step, 1.75M params):
- テクスチャは生成された (grain 0.63 -> 1.27)。**機構は動く**
- しかし**平坦部を悪化**させた。空・階調・暗部に斑。黄色いボケは濃い塊+黒点に

G1 第2版 (スケール正規化, 同じ 3,000 step):
- **平坦部の修正は完全に成功**。斑が消え、以後も再発なし (平坦部追加振幅 0.0168 < StageF の 0.0230)
- grain 0.934 で LaMa (0.943) とほぼ同値になったが、**中身はノイズ**。目視で青黒い粒々

G1 第3版 (9,000 step = 3倍, 同設計):
| step | grain | 平坦部 |
|---|---|---|
| 1500 | 0.891 | 0.0156 |
| 4500 | 0.957 | 0.0150 |
| 9000 | 0.923 | 0.0138 |
**grain は step 4500 で頭打ち。目視でも粒は粒のまま、構造にならなかった。**
事前に決めた撤退基準に該当したため撤退。

**結論**: 拡散/フローの原理が誤りとは言えないが、**この計算資源 (M1、9,000 step で16時間) では

「1万枚から汎用的な残差分布を学ぶ」本件とは条件が異なっていた。

**再利用可能な成果**: `residual_scale` (既知画素のみからの局所振幅推定、漏洩なしをテストで担保)。
平坦部で生成を抑える仕組みとして、他の生成手法にもそのまま使える。

## 実物体マスクの構築 (2026-08-25) — 途中経過と、避けた誤り

**目的**: §3.1 で判明した「マスク辞書に人物クラス判定が無い」問題を是正し、
**実際の除去課題**で LaMa と YOEO を比べる。同時に §3.3 の M2 (対象の実サイズ) を測る。

**検出器**: SAM3 は使えなかった。キャッシュにあるのは `Sam3VideoModel` (動画追跡用) で、
かつ `transformers 4.57.6` に `Sam3Model` が無い (対応は 5.x 以降。diffusers を守るため
5 未満にピンしている)。→ torchvision の **Mask R-CNN v2 (COCO, person=1)** を使用。
人混みタイルで 10 人を score>0.7・最高 0.996 で検出することを確認。

**踏みかけた罠**

ショット名 (公園・寺社・動物園など) で絞ると検出率が **0.3% -> 31.9%** に跳ね上がった。
数値だけなら「当たりを引いた」と見える。**しかし中身は全て誤検出だった** —
チューリップの前ボケを score 0.98 で「人物」と判定していた。23 件すべて同一画像由来。

原因は構造的: タイルは 26〜40MP からの**原寸 512² 切り出し**でシーンの文脈が無く、
COCO 学習の検出器 (800px の場面全体を前提) は拡大された前ボケを大物体と誤認する。

そのまま集計していれば「**消したい対象は中央値 495×464px、面積 58%**」という
結論を報告していた。§3 で「対象は小さい」と誤ったのと**向きが逆なだけで同じ型**である。

**分離できることを確認**

鮮鋭度比 = (マスク内の高周波エネルギーの std) / (タイル全体の std):

| | 検出 | 面積 | サイズ | 鮮鋭度比 | 判定 |
|---|---|---|---|---|---|
| 人混みタイル `X-T4_DSCF6281_018` | 12 件 | 1.4〜2.0% | 87〜127px | 0.79〜1.83 | 全て採用 |
| 前ボケタイル `X-T5_DSCF3669_020` | 1 件 | 78.0% | 507×500 | **0.19** | 棄却 |

**面積では絞らない。** 絞れば「対象は小さい」という結論をフィルタ自身が作ることになり、
§3.1 で撤回したのと同じ誤りになる。鮮鋭度比は**誤検出という別種の誤り**を落とすもの。

**限界 (記録しておく)**: タイルには文脈が無いので、検出器は本来の性能を出せない。
この経路で得られるサイズ分布は「タイル内に収まり、かつピントが合っている人物」に
偏る。**§3.3 の M1 (実写真での実測、外部ストレージの再接続が必要) が本命として残る。**

ハードウェアの制約 (512² のみ実用) が**衝突している**。
主用途は 512² で足りるが、中景以上には縮小→復元 (L4) が要る。

### 判定基準の追加 (ユーザ、2026-08-25)

> 「テクスチャはいいのに**周りと馴染んでない色がマスクと同じ形になっている**点が多くあった」

**これは生成能力ではなく合成の問題である。** 敗因の分類を 2 つに分けて考える必要がある:

  (A) 破綻した人体の生成 — 生成モデル側の問題
  (B) **マスク形の色斑** — 合成側の問題。**設計上 L5 で直す想定のもの**

(B) が多数を占めるなら、YOEO の 32 敗は**モデルの実力ではなく結合の欠陥**による。
最有力の原因は **VAE 往復の色ずれ**: `where(mask, 出力, 原画像)` で合成すると
マスク内だけが VAE を通った色になり、差がマスクの形に出る。

## 結合の検証で見つかった欠陥 (2026-08-25) — 入力が学習分布から外れていた

ユーザ指摘「テクスチャはいいのに**周りと馴染んでない色がマスクと同じ形になっている**」を
起点に、飛ばしていた結合の検証を実施した。

**調べて外れた仮説 2 つ**
1. **VAE 往復の色ずれ** — 実在した (平均 −0.52%、G −1.19%) が、
   実際のマスク境界の色差 (±0.02〜0.06) の 1/4〜1/10 でしかない
2. **合成による色斑** — Poisson / 大域加算 / 低解像度オフセット場の 3 通りを試したが、
   どれも「素の合成」より良かったのは 8〜10/16 件で偶然と大差なし。
   **色斑は合成ではなく生成された内容そのもの**だった

**見つかった真の欠陥: モデルへの入力が暗く低コントラストだった**

`Yoeo.__call__` は `Lama.__call__` から正規化を写しており、
`k = max(1.0, percentile(p, 99.9))` の **下限 1.0** が原因で
「画像全体より暗いクロップ」を暗いまま渡していた。

| | 修正前 | 修正後 | 普通の写真 |
|---|---|---|---|
| 平均輝度 中央値 | 0.346 | 0.388 | 0.45〜0.55 |
| 標準偏差 中央値 | **0.128** | **0.203** | 0.20〜0.25 |

### マスクの精度について — ベンチは現状のまま進める (ユーザ判断 2026-08-25)

**採用する。** 実運用でマスクは雑に描かれるので、
精度の高いマスクを前提にしたベンチは**ユーザが経験しない条件**を測ることになる。

## パイプライン (L1〜L5) の実装と L4 の実測 (2026-08-25)

**これまで存在しなかったもの。** Phase 0 では 512² クロップを受け取る除去器と、
ベンチ生成に埋め込まれた切り出しコードしか無く、
「写真とマスクを渡したら結果が返る」実体が無かった。`nagi_inpaint2/pipeline.py`。

**確認できたこと**

| | 実測 |
|---|---|
| **51MP** の画像で `patch()` | **7.1 秒** (512² 単体 5.7 秒とほぼ同じ) |
| マスク外のビット一致 | ✅ (Poisson を含め一切触らせない) |
| 計算量 | **マスク面積のみに依存**。画像サイズに依存しない (SPEC §1.1 の要求) |

`__call__` は画像全体を複製するので 100MP では複製だけで十数秒かかる。
**大きい画像では `patch()` を使う**こと (変更した矩形だけを返す)。

### L4 (縮小して押し込む経路) の損失

既存の 512² ベンチを `crop=256` で処理させ、**2 倍の縮小を強制**した。
`crop=512`(ネイティブ) が参照になるので、L4 の損失だけを切り出せる。

| | grain | 継ぎ目 | 参照との知覚距離 |
|---|---|---|---|
| 参照 (512 ネイティブ) | 0.781 | 1.06 | 0 |
| 縮小 2 倍・復元なし | **0.622** | 1.04 | 0.00465 |
| 縮小 2 倍・HF 移植 | **0.828** | 1.05 | 0.00496 |

**縮小 2 倍で grain が 0.781 -> 0.622 (−20%) 落ちる。** HF 移植で 0.828 まで戻る。
ただし**参照との知覚距離は改善しない** (むしろ +7%)。
参照自体も補完結果であって正解ではないので、この指標だけでは優劣を決められない。

### HF 移植の初版にあったバグ — **消したい物体のテクスチャを戻し入れていた**

```python
hf = _highpass(sub)          # sub = 元のクロップ (物体が写っている)
add[sm] = hf[sm] * (...)     # ← マスク内 = 物体そのものの高周波
```

grain は 0.622 -> 0.718 と「回復」したのに、参照との知覚距離が
0.00465 -> 0.00468 と全く動かなかったのが手がかりだった。
**grain だけを見ていたら「効いた」と報告していた。**

正しくは、穴の各画素について**マスク境界をまたいで鏡像の位置**にある
既知画素の高周波を採る (`p_src = 2*p_nearest - p_hole`)。
最近傍の複製だと筋になるので反射させる。

**陰性対照を置いた**: 穴に人工の「物体」を置き、
注入した高周波がその物体の高周波と**相関しないこと**を確認する。

    注入した高周波と物体の高周波の相関: +0.0098  (初版なら 1.0 付近)
    注入後の穴の grain: 1.045 (1.0 が周囲と同等)

## L4 の拡大に Real-ESRGAN を試して棄却 (2026-08-25)

ユーザ提案「拡大に最新の AI を使うのは無し? realesrgan とか」を受けて実施。
**R17 (自作の前に既存を試す) を私が破っていた** — 手作りの HF 移植を書く前に
学習済み超解像を調べるべきだった。

**Real-ESRGAN x2plus** (公式 `xinntao/Real-ESRGAN`、**BSD-3-Clause**、
16.7M params、67MB)。`basicsr` は依存が重く既知の非互換があるので RRDBNet を直接実装し、
**`load_state_dict(strict=True)` が 702 テンソル全一致で通ることを検証**した。

速度は問題なし: 256²->512² **0.45 秒**、512²->1024² 1.80 秒、ピーク 1.19GB。

**正解のある比較で棄却** (元の 512 画像を縮小 -> 拡大し、元画像と比べる):

| 縮小率 | 手法 | 知覚距離↓ | PSNR↑ | 高周波 (100% が目標) |
|---|---|---|---|---|
| 2倍 | bilinear | **0.00126** | **40.90** | 48% |
| 2倍 | Real-ESRGAN | 0.00289 | 30.89 | **172%** |
| 4倍 | bilinear | **0.00286** | **35.37** | 35% |
| 4倍 | Real-ESRGAN | 0.00433 | 26.49 | **208%** |

**bilinear より悪い。** 高周波を元画像の 172〜208% 作っており、過剰である。

**理由**: Real-ESRGAN は**ぼけ・ノイズ・JPEG という実世界の劣化**を戻すよう
学習されている。こちらの入力は高品質な写真を**きれいに縮小しただけ**なので、
モデルは過剰に detail を足す (いわゆる「AI 拡大がカリカリになる」現象)。
実際、継ぎ目が 1.05 -> 1.15 に悪化した (穴の中だけ周囲より鮮鋭になるため)。

**用途との食い違い**: 穴の中には復元すべき正解が存在しない。
目標は「detail の最大化」ではなく「**周囲との整合**」である。
Real-ESRGAN は前者を最適化する。HF 移植は周囲の高周波を持ってくるので後者が揃う。

**未検討**: bicubic 縮小で学習された古典 SR (SwinIR classical / EDSR) なら
劣化の種類が一致するので、bilinear と ESRGAN の中間に落ちるはず。
ただし「周囲と揃える」という目標には直接は効かない。

**副産物**: 「参照 (512 ネイティブ) との知覚距離」は品質指標として**成立しない**ことが
目視で確認できた。拡大表示すると、参照が明るい空白の帯を作り、
縮小した系列の方が妥当な物体を補完している例があった。
参照自体が補完結果であって正解ではない。

### 盲検A/Bの結果: **視野4倍は有意に悪い** (2026-08-30、判定=ユーザ)

上の「初めての改善」は**目視で覆った。6 度目の指標と人手の不一致**である。

**まず判定用の画像そのものに欠陥があった** (ユーザ指摘「A/Bで表示されている
箇所が違うので判定できません」)。広視野側の出力を **1024 の画角のまま**並べていたため、
元画像・マスク・512原寸 の 3 コマと**別の場所を見比べさせていた**。
広視野側も 1024 で合成まで済ませ、**512原寸と同一の領域を切り出して**並べ直した
(`eval/ab_context.py`)。2 つのベンチが同じ場所を指すことは実測で確認した:
native 領域の画素差 max **0.000000** (ビット一致)、マスクの IoU 中央値 **1.000**。

**結果** (差が大きい上位 20 件、広視野を A に 10 件・B に 10 件と厳密に半々)

| | 件数 |
|---|---|
| **512 原寸の勝ち** | **12** |
| 広視野 (1024→512) の勝ち | 1 |
| どちらも良い | 1 |
| **どちらもダメ** | **6 (20件中 30%)** |

**勝率 7.7% (n=13)、両側二項検定 p = 0.0034。**
左右の偏りではない (広視野が A 側での負け 5 / B 側での負け 7)。

**負け方**: 穴の中が**構造ごと潰れる**。細部が甘いのではない。

  - 欄干の桟が消えて灰色の板になる (`01_24_DSCF4433`)
  - 煉瓦の目地が溶けて壁が滑らかな諧調になる (`09_50_DSCF9994`)

縮小 2 倍で高周波は 26% しか残らない。**HF 移植は統計 (grain) を戻すだけで、
桟や目地のような構造は戻せない。** grain 0.852 は「周囲と同じ粗さ」を意味するだけで、
「正しいものが描かれている」ことは意味しない。継ぎ目 1.07 も同様に、
**中身が潰れていても継ぎ目は綺麗**でありうる。指標がどちらも
「潰れ」を検出できない構造だったので、上の表の 7→4 は判断材料にならなかった。

**確定した結論**

1. **クロップは 512 原寸を維持する。** 視野を広げる方向は閉じた。
2. **L4 (縮小して押し込む経路) は思っていたより高くつく。**
   512² に収まらない 31% の対象は、この経路を通る以上
   **12対1 で負ける品質**になっている。ここは別途手当てが要る。
3. 残りの仕事は **6/20 = 30% の「どちらもダメ」** に集中している。

## コアの入れ替え: RORem — **採用しない** (2026-08-30、判定=ユーザ)

「自然な補完」で 6 本連続の空振りが出た後、**同じコアのつまみを回すのをやめて
コアそのものを入れ替える**方針で試した唯一の未検証候補。

**入手**: `LetsThink/RORem` (HF、**Apache-2.0**、6.5GB)。完全な diffusers
パイプラインで、`unet/config.json` の `_name_or_path` が **`RORem_mixed`**
(512/1024 両対応版) を指す。`in_channels=9` を確認。
土台の `stable-diffusion-xl-1.0-inpainting-0.1` は**別途不要**だった。

推論は本家 `inference_RORem.py` から書き写した (50 step / `guidance_scale=1.0` /
`strength=0.99` / 固定プロンプト)。

> **本家コードの読み取り**: `use_CFG=True` の枝は negative_prompt を渡すが、
> **`guidance_scale=1.0` では diffusers は CFG を回さない**ので実際には効いていない。
> 効いているのは positive 側の固定文だけである。

**M1 実測**: 62.8 秒/箇所 (50 step、512²、fp16)。YOEO 2step の 5.3 秒の **12 倍**。
プロンプトが固定なので埋め込みを 1 度だけ作りテキストエンコーダ 2 本を捨てた (fp16 で 1.64GB 節約)。

### 盲検A/B (差が大きい上位 20 件、A/B を厳密に半々)

| | 件数 |
|---|---|
| **YOEO 2step の勝ち** | **12** |
| RORem 50step の勝ち | 5 |
| どちらも良い | 0 |
| どちらもダメ | 3 (15%) |

**YOEO 勝率 70.6% (n=17)、両側二項検定 p = 0.1435。有意ではない。**
つまり「RORem が劣る」ことは示されていない。示されたのは
**「12 倍の時間を払って勝てていない」**である。論文の人手評価
(RORem 76.2% 対 LaMa 55.4%) は再現しなかった。

**参考の自動指標** (全 60 件、対照: 消す前に人物が検出できたのは 56/60)

| | 継ぎ目 | grain | 人物残存 | 新規物体 | 秒/件 |
|---|---|---|---|---|---|
| YOEO 2step | 1.069 | **0.849** | **8/60** | **1/60** | **5.3** |
| RORem 50step | **1.042** | 0.675 | 12/60 | 3/60 | 62.8 |

### 負け方: **消した対象と同じ形の暗い残像**

拡大して見ると 3 件とも同じ形をしていた — 人物のシルエットが薄く残る、
ベンチの上に黒い塊が乗る。**継ぎ目 1.042 は YOEO より良いのに中身に残像がある。**
R21 の実例がもう 1 つ増えたことになる (継ぎ目も grain も「中身の正しさ」を測らない)。

### 2 つの機構仮説を立てて、**両方とも実測で否定した**

1. **マスクが本家の想定より細い**。本家既定は `dilate_size=20`、こちらのベンチは
   6px 膨張のみ。**これは私が本家レシピから外していた点**なので確かめる価値があった。
   → 膨張 12 / 20 で試すと**残像は薄くなるが消えない**。
   そして**穴が広がった分だけ新しい捏造が増える** (周囲の人物の形が変わる、にじみが出る)。
   差し引きで良くなっていない。

2. **`strength=0.99` が元画像を漏らしている**。diffusers の inpaint は
   `strength < 1.0` のとき初期潜在を `add_noise(image_latents, noise, t)` にする
   (`strength == 1.0` のときだけ純ノイズ)。t≈981 でも
   `image_latents`(振幅~1) + `noise*sigma`(sigma~14) で **SNR 7% 程度**残るので、
   明るい背景の中の暗い人物という**強い低周波**が通ると考えた。
   → **外れ**。`strength=1.0` にしても残像はそのまま。

   > **no-op を疑って数値で確かめた**: 出力は確かに変わっている
   > (穴の中の平均差 0.030 / 最大 0.211、diffusers 0.39.0 の
   > `prepare_latents` が `is_strength_max` を使うことも確認)。
   > **変わった上で残像が残る**ので、仮説の否定として成立する。

**結論**: 残像は**レシピの逸脱ではなくモデルの性質**である。
12 倍の時間を払う理由が無いので RORem は採用しない。
`nagi_inpaint2.removers.RORem` と重み (`models/rorem`) は再現用に残す。

**副産物**: これで **L3 の候補 (LaMa / YOEO / SmartEraser / RORem) を出し尽くした。**
「既存のコアを差し替えれば勝てる」という道は閉じた。

## M1 での**学習**コスト実測 (2026-08-30) — D の見積もりの根拠

§13 は**推論**だけを測っていた (SD1.5 UNet 1 step 1082ms)。
「YOEO の UNet に LoRA を当てる」が現実的かどうかはこの数字で決まるので測った。

SD1.5-inpaint UNet (859.5M、config から構成。**速度は重みの値に依らない**)、
LoRA r16 を注意の to_q/k/v/out に注入 (可訓練 3.19M)、
潜在 64² (=512²)、fp32、AdamW、順伝播+逆伝播+更新の 1 step:

| batch | 1 step | 1 枚あたり | MPS ピーク |
|---|---|---|---|
| **1** | **2,908 ms** | 2,908 ms | **11.62 GB** |
| 2 | 86,712 ms | 43,356 ms | 18.11 GB |

**batch 2 は使えない。** 18.11GB は 16GB 機の物理メモリを超えており、
スワップして 1 step あたり **30 倍**に落ちる (§10.1 の 11.9 s/step 前例と同じ形)。

**したがって M1 での学習は「batch 1、2.9 秒/step、ピーク 11.6GB」が上限。**
連続運転の減速 (§13 の ×1.38) を入れると実効 **約 4.0 秒/step**。
可訓練パラメータを減らしても**逆伝播は UNet 全体を通る**ので、
LoRA にしても 1 step の重さはほとんど変わらないことに注意
(節約できるのは optimizer 状態のメモリだけ)。

**換算**

| やりたいこと | 実 step 数 | 連続運転での所要 |
|---|---|---|
| 実効 batch 4 × 5,000 step | 20,000 | **22 時間** |
| 実効 batch 8 × 10,000 step | 80,000 | **3.7 日** |
| 実効 batch 8 × 50,000 step | 400,000 | **18.5 日** |

公開 LoRA の学習レシピは実効 batch 8〜16 で 1万〜5万 step が普通なので、
**M1 では「下限のレシピを 1 回試すのに 4 日弱、機械は他に使えない」**が実態である。
ピーク 11.6GB なので学習中は他の作業ができない。ファンレスの熱制限もこれに乗る。

> **緩和策 (未測定)**: 勾配チェックポイントで活性メモリを落とせば batch 2 が入る
> 可能性がある (計算は約 +30%)。入れば 1 枚あたりは改善する。
> **測っていないので見積もりには入れない。**

## L6 検品 (Phase 2) を落とす — **採否はユーザが決める** (2026-08-30、ユーザ判断)

C (壊れを自動検出して退避する層) を検討した結果、**作らないことにした**。

**理由**: ShadeWave は写真アプリなので、**結果を見せて採否をユーザに委ねられる**。
そこには**精度100%の判定者が既に居る**。手持ちの信号の分離能力は最良でも
AUC 0.700 (継ぎ目) だったので、**100% の判定者の隣に 0.700 の代替を置く意味がない**。

検討の過程で測ったこと (残しておく):

| 信号 | 既知の失敗 8 件で反応 | 正常 52 件で誤反応 |
|---|---|---|
| 人物残存 (Mask R-CNN, 46.4M, 733ms, 常駐 2.44GB) | 3/8 | 5/52 |
| 新規物体 | 1/8 | **0/52** |
| 継ぎ目 | AUC **0.700** | — |
| grain | 0.804 対 0.854 (重なる) | 実質無力 |

また **LaMa への退避は「全部ダメ」を救わない**ことも確認した
(3 者比較で全部ダメ 4/16 = 25%、そこでは LaMa も失敗している)。

### この決定が評価の枠組みを変える

**1 発勝負ではなくなった。** したがって:

1. **測るべき数字が「LaMa への勝率」から「採用率」に変わる。**
   Phase 0 の合格条件 (判定 40 件で 27 勝) は、
   「1 つの出力を出荷する」前提で書かれていた。前提が消えた。
2. **候補を複数出すのが自然になる。** 実測 (実除去ベンチ 60 件、L5 込み):

   | | 秒/件 |
   |---|---|
   | LaMa | **0.63** |
   | YOEO 2step | 5.3 |
   | 両方 | **5.9** |

   **2 案出しても 5.9 秒。** 3 者比較では YOEO が最良 6/11・LaMa が最良 3/11 で
   得意な場面が割れていたので、並べて選ばせる形と噛み合う。

3. **我々は「採用できるか」を一度も測っていない。** 手持ちの判定は全て比較
   (A/B、3 者) で、絶対値は「全部ダメ」の率しかない
   (25% / 30% / 15% — いずれも「差が大きい上位」に絞った集合での値で、全体の率ではない)。

> **R23: 製品の使われ方が変わると、合格条件も変わる。**
> 「LaMa に勝つ」は出荷する 1 枚を機械が選ぶ前提の目標だった。
> ユーザが選ぶなら、問うべきは**「候補の中に採用できるものがあるか」**である。

## 採用率の実測 (2026-08-30、判定=ユーザ) — **偏りのない全 60 件での初めての絶対値**

R23 に従い、聞き方を「どちらが良いか」から「**それぞれ単独で採用できるか**」に変えた
(`eval/accept.py`)。左右は伏せ、LaMa が A 側にちょうど 30/60。並び順も無作為化。
出力は全てキャッシュ済みなので**新しい計算は発生していない**。

| | 採用可 | 採用率 | 95%信頼区間 |
|---|---|---|---|
| LaMa 単独 (0.63 秒) | 38/60 | 63.3% | [50.7%, 74.4%] |
| YOEO+L5 単独 (5.3 秒) | 45/60 | 75.0% | [62.8%, 84.2%] |
| **2 案を出す (5.9 秒)** | **53/60** | **88.3%** | **[77.8%, 94.2%]** |

内訳: 両方可 30 / LaMa だけ 8 / YOEO だけ 15 / **両方ダメ 7 (11.7%)**

McNemar 正確検定 (不一致 23 件、8 対 15): **p = 0.2100**。
**YOEO が優勢だが有意ではない。** 3 ラウンドの比較判定と同じ結論
(ab_removal 56.2% / 3 者 p=0.12 / ab_cores) で、
**一貫して「YOEO がやや上、ただし決定的ではない」**が出続けている。

**2 案にすることの上積みは +13.3 点** (75.0% -> 88.3%)、費用は +0.63 秒。
LaMa だけ可が 8 件あるので、**LaMa は YOEO の劣化版ではない**。得意な場面が違う。

### 「マスクが悪いせいでは」を測った (ユーザ指摘)

ベンチのマスクは検出結果を拡大して 6px 膨張したもので、ユーザが描いたものではない。
元画像に Mask R-CNN を掛け、**マスク内に重心がある人物**の何割がマスクに覆われているか
(被覆率) を測った。56/60 で人物を検出できた。

| | 被覆率 中央値 | 0.9 未満 |
|---|---|---|
| 両方ダメ 7 件 | 0.972 | 2 件 |
| 採用可 53 件 | 0.989 | 10 件 |

**マスクは主因ではない。** 両方ダメ 7 件のうち 5 件は被覆率 0.9 以上
(うち 3 件は 0.97〜1.00)。ただし**部分的には当たっている**:

| | 不採用のうち被覆率 0.9 未満 |
|---|---|
| LaMa | 7/22 = **32%** |
| YOEO | 3/15 = 20% |
| (全体の基準) | 12/60 = 20% |

**LaMa の失敗にはマスクの粗さが効いているが、YOEO には効いていない。**
なお「マスクを膨らませる」は YOEO で既に実測して改善せず、
RORem では新しい捏造を増やした (2 回とも否定的)。

### 両方ダメ 7 件の中身

| 壊れ方 | 件数 |
|---|---|
| **人混み・隣接** (対象が他人と接している) | 5 |
| **ボケた人物** (前ボケ/後ボケ、同一写真 DSCF6261 の 2 件) | 2 |

**構造の破綻は 0 件。** 「どちらもダメ」の内訳が前回 (構造 4 / 人混み 4) と変わったのは、
前回が「差が大きい上位 20 件」という偏った集合だったため。
**偏りのない 60 件で見ると、残った失敗はほぼ人混みである** (ユーザが対象外と決めた領域)。

> **R24: 「残った仕事は何か」は、偏った集合の上で数えてはいけない。**
> 上位 N 件に絞った集合で数えた内訳 (構造 4 / 人混み 4) は、
> 全 60 件で数え直すと (構造 0 / 人混み 5 / ボケ 2) になった。
> **D (構造に効く層) の見積もりはこの誤った内訳の上に乗っていた。**

## 2 案を返すパイプラインの統合と 1 億画素での確認 (2026-08-30)

`MultiInpainter` を追加した (`nagi_inpaint2/pipeline.py`)。
**クロップは 1 回しか取らず**、切り出し・縮小をコア間で共有する。
`eval/verify_100mp.py` で通しを確認した。

| 画素数 | `patches()` | 基準比 |
|---|---|---|
| 0.3MP (512²) | 7.58 s | 1.00x |
| 4.2MP (2048²) | 7.29 s | 0.96x |
| **104.9MP (10240²)** | **11.56 s** | 1.53x |

**マスク外は両候補・全サイズでビット一致** (SPEC §9.1)。RSS は 7.07GB で一定。

### 検出した欠陥: 画像全体を複製していた

`patches()` / `patch()` の冒頭が
`img = np.ascontiguousarray(img.astype(np.float32))` になっていた。
**切り出す前に画像全体を float32 で複製**するので、100MP では 1.26GB の複製が入る。
「費用は画素数に依存しない」という設計上の主張が壊れていた
(実測 4.2MP 7.95 秒に対し 100MP 13.82 秒)。
**切り出してから型変換する**形に是正 -> 13.82 秒が 11.56 秒に。

### 残っている 1.53 倍の内訳 (実測)

| | 4.2MP | 104.9MP |
|---|---|---|
| `crop_box` (マスク全体の走査) | 9.2 ms | **246.7 ms** |
| LaMa 推論 | 0.83 s | 0.63 s |
| YOEO 推論 | 5.41 s | **7.12 s** |

**算法的な画素数依存ではない。**
`crop_box` の 247ms は `np.nonzero` が 105M 要素を走査する分で、
呼び出し側 (ShadeWave はユーザがマスクを描いた位置を知っている) が
外接矩形を渡せば消せる。**YOEO の +1.7 秒はメモリ圧**で、
1.26GB の画像とモデル 7GB を同時に抱えることによる。
アプリでは画像はどのみち常駐しているので、この分は二重計上になる。

### 守りを増やした

`tests/test_multi.py` (9 件、**モデルを読まない**。偽コアは穴の外も塗りつぶすので、
合成側が守っていなければ落ちる):

  - マスク外がビット単位で原画素
  - 2 案が別物であること (同一なら並べる意味がない)
  - 入力画像を破壊しないこと
  - **`float16`/`float64` を渡しても入力の型が変わらないこと**
    (= 全体を複製していないことの検査。上の欠陥の再発防止)
  - マスクが画像の端にあっても範囲に収まること
  - マスクが空なら無変更
  - `__call__` は貼った矩形の外が原画素のまま

## Qwen-Image 2.1 の検証 1: M1 16GB で回るか (2026-10-21) — **不採用 (2026-10-26、ユーザ判断)**

> **破棄済み**: 重み (`models/qwen21-turbo-mflux-q4`、9.9GB)、検証用の pixi 環境と
> 計測スクリプト (`tools/mflux_env/`)、出力 (`out/qwen21_bench/`) はゴミ箱へ移した。
> 計測スクリプトはコミットしていないので、再検証するときは下の手順から作り直すこと。
> 再検証の条件: **M1 で 1024² が数十秒以内**に収まる経路 (より軽い蒸留版・高速化) が出たとき。


**構成**: `OsaurusAI/Qwen-Image-2.1-Turbo-mflux-4bit` (9.9GB。7B の本体と Qwen3-VL-8B の
テキスト/ビジョンエンコーダを MLX 4bit、VAE は fp32)。公式 Turbo = 8 step、CFG なし。
mflux 0.23.0 の編集モードで**マスク指定の除去**を実際の使い方どおりに回した。
入力は実除去ベンチの case 24 (欄干の前の人物)。`--compute-precision float16` (M1 向け)。

**重みの選定理由** (再検索の結果): テキストエンコーダまで量子化されているのは
MLX 系だけだった。公式 bf16 は 33GB (エンコーダだけで 17.5GB)、GGUF は本体のみで
エンコーダが別途要る。mflux (MIT) が Qwen-Image 2.1 のマスク指定と M1 用 float16 に対応。

**環境** (破棄済み): 本体とは別の pixi 環境を作った。mflux は torch>=2.13 を要求し、
本体の固定 (torch<2.13) と衝突するため。途中で 3 つ詰まった:
mlx のホイールが macOS 14 以上にしか無い / conda の numpy と pip の torch で
libomp が二重に載る / Pillow 13.0.0 が Python 3.15 の遅延 import 前提で 3.11 では import 時に落ちる。

| 設定 | 1 件 | MLX ピーク | スワップ |
|---|---|---|---|
| 1024²、省メモリなし | 440〜538 s | **22.5GB** | 0.6 -> **13.5GB** |
| 1024²、省メモリ (low-ram 相当) | **599〜638 s** | 10.3GB | 増えない (約 3GB のまま) |
| 1024²、省メモリ、参照画素予算 512 | 542〜545 s | 10.2GB | 増えない |
| 512²、省メモリ | 142〜145 s | 10.2GB | 増えない |
| (参考) 現行 YOEO+L5 / LaMa / 2 案 | 5.3 / 0.63 / 5.9 s | 7.1GB (常駐) | — |

**落とし穴**: mflux を **Python API から直接呼ぶと、CLI が自動で掛ける省メモリ処理
(エンコード後にテキストエンコーダを捨てる、キャッシュ上限、VAE タイル) が効かない**。
最初の 22.5GB はこのため。同じ処理を自分で掛けると 10.3GB に収まる。
ただし編集モードはエンコーダが入力画像そのものを見るので、**エンコーダを捨てると
次の画像で読み直しになる** (埋め込みを使い回せない)。

**マスク外は全設定で完全一致** (最大差 0.0000。mflux が最後に画素で合成している)。

**結論: 回るが、実用速度ではない。** 推奨解像度 1024² で **1 箇所 9〜10 分**、
現行の 2 案 (5.9 秒) の **約 100 倍**。ファンレスの熱で 2 回目が遅くなる傾向もある
(440 -> 538 s)。512² なら 2.4 分だが、mflux の文書は「Turbo は 1024 未満で
細部が画素の格子になる」と明記している。

**画質の一瞥 (1 件だけ、判定ではない)**: case 24 では LaMa と YOEO が欄干を
きれいに繋いだのに対し、Qwen は 1024² で桟が途切れてぶら下がり、512² では
対象の輪郭に沿った明るい残像が出た。**n=1 なので結論ではない。**
