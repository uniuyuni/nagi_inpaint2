## 1. v1 が負けた理由の、正しい一般化

v1 では 4方向 10手法が失敗した。個別の敗因は記録済み (SPEC §12〜§18) だが、
**再設計にとって重要なのは共通する 1 点だけ**である。

### 1.1 平均値回帰は「損失と目標分布」の性質であって、モデルの性質ではない

穴の中の正解は**一意に決まらない**。同じ入力に対して、もっともらしい出力が多数ある。
この状況で L1 / L2 / 知覚距離のような**点推定の損失**を最小化すると、最適解は
「もっともらしい出力たちの平均」になる。平均は必ずぼける。これは学習量・モデル容量・
アーキテクチャと**無関係**な、損失関数の数学的性質である。

v1 で試したことを、この観点で整理すると:

| 試したこと | 分類 | なぜ効かなかったか |
|---|---|---|
| Stage F (L1 学習) | 点推定 | 定義通り平均に収束。grain 0.176 |
| 知覚損失追加 | 点推定 | 知覚空間での平均に変わっただけ |
| WTA 多仮説 ×2 | 分布近似 | 仮説が崩壊（相互差 4.4e-8）。小規模では安定しない |
| GAN ×2 | 分布損失 | 原理的には正しいが、M1 規模で安定させられなかった |
| 残差フロー ×3 | 分布損失 | 原理的には正しいが、残差の学習可能性が足りなかった |
| ブロックコピー各種 | 非パラメトリック | 平均化はしないが、穴の内部に「文脈上正しい」テクスチャを置けない |

**分布を扱う方向（GAN・フロー）は原理的に正しかったが、M1 単体・自前データのみの規模で
安定に学習できなかった。** これが v1 の総括である。

### 1.2 したがって、選択肢は 3 つしかない

穴の中を「ぼけずに」埋めるには、以下のいずれかが必要である。

- **(a) 分布から標本を引く** — 拡散モデル。学習が安定しており、実績が圧倒的。
- **(b) 分布損失で学習する** — GAN。v1 で 2 回失敗。M1 規模ではリスクが高い。
- **(c) 目標を一意にする** — 教師の出力を目標にする（蒸留）。目標が入力の決定的関数に
  なるので、**L1 で学習しても平均化が起きない**。

v2 は **(a) を中核に据え、(c) で軽量化する**。(b) は使わない。

### 1.3 v1 自身の測定が、この方針を支持している

`eval/RESULTS.md` に、v2 の設計判断を直接裏づける記述が3つある。

**① 生成の事前分布は、M1 でゼロから学習できない（実測済み）**
> 「拡散/フローの原理が誤りとは言えないが、**この計算資源 (M1、9,000 step で16時間) では
> 空間構造の学習に到達できない**」(Stage G 撤退の結論)

これは「学習済みの生成事前分布を持ってくる」以外に道がないことの、自前の実証である。

**② 多仮説が失敗した理由も、損失の性質だった（実測済み）**
> 「WTA は『K個の仮説の間で平均しない』ことは保証するが、**各仮説は自分が勝つケース集合の
> 中で依然 L1 で学習される**ため、その集合が多峰的ならやはり平均を出してぼける」

§1.1 の一般化が、v1 の測定によって既に確認されている。

**③ LaMa の絶対品質も、この用途では高くない（ユーザ判定）**
> 「『同等』の4件は『両方良い』ではなく**『両方悪い』** — 片方はディティールがおかしく、
> 片方はぼけている。**LaMa もそこでは失敗している**」

**これは勝算にとって重要な情報である。** 越えるべき壁は「完璧な LaMa」ではなく、
「同じ場面でしばしば失敗する LaMa」である。除去専用に学習された拡散モデルが
論文どおりの性能を出すなら、差は開きやすい。

> ### ⚠ 2026-08-25: (c) は実測で**反証された** (Phase 0b、eval/RESULTS.md)
>
> LaMa を決定的教師として 2 arm 対照実験を行った結果、
> **目標を「正解画像」から「決定的教師の出力」に替えても、ぼけは消えなかった。**
> 生徒は教師の 1.55倍遠く、grain 0.22 対 0.914、
> しかも**「正解画像を単にぼかしたもの」より 1.99倍悪い**。
> 2 つの arm は目視で見分けがつかず、基準を替えると差の符号が反転した (実質差なし)。
>
> **ぼけの主因は目標の多峰性ではなく、生徒側の容量・最適化だった**
> (§4.2.1 で (c) として自認していた抜け穴が、実際に効いていた)。
> 以下の理屈は目標側については依然として正しいが、
> **それだけでは鮮鋭な生徒は得られない**。

> **(反証前の記述)** (c) の性質は理屈として厳密で、
> 「教師の出力 y = T(x, seed固定) は x の決定的関数 → 条件付き分布が
> デルタ関数 → 平均 = その値 → L1 最適解はぼけない」。
> v1 で 10 手法が失敗した原因が、構成上ここで消える。

## 2. 外部知見の調査結果（2026-08 時点）

物体除去は 2025〜2026 に専用モデルが多数出ており、**汎用インペインティングとは別のタスク**
として扱われるようになっている。LaMa との比較値が論文に載っているものを挙げる。

| 手法 | 基盤 | ステップ | 重み（一次情報で確認済） | ライセンス | LaMa との比較（論文値） |
|---|---|---|---|---|---|
| **SmartEraser** (CVPR'25) | SD1.5-inpaint + CLIP誘導 | 多ステップ | GoogleDrive / BaiduDrive | **MIT** | FID **10.90** vs LaMa 20.03 / 人手選好 56% vs 16% |
| **YOEO** (2026) | SD1.5-inpaint + LCM | **2** | HF `unhzyx/yoeo` (`yoeo.pth` 3.44GB) | **Apache-2.0** | 0.21 s/枚。余計な物体の生成を損失で抑制 |
| **RORem** (2025) | SDXL-inpaint + LoRA | 15〜30 / **4** (LCM) | HF `LetsThink/RORem` + GDrive | Apache-2.0（論文本文は CC BY 4.0 と記載。**要現物確認**） | 成功率 **76.2%** vs LaMa 55.4% |
| ObjectClear (CVPR'26) | 物体+影の同時除去 | 多 | 公開済 | **NTU S-Lab（非商用）→ 除外** | PowerPaint/RORem より人手選好で優位 |
| FlashClear (2026) | ObjectClear + 4step蒸留 | 4 | 未確認 | 未確認 | ObjectClear比 8.26倍速 |
| PowerPaint v2 (ECCV'24) | SD1.5 + BrushNet | ~30 | HF | Apache-2.0 | FID 21.23 — **LaMa 20.03 より悪い** |

> **ライセンスの重層構造に注意**: SmartEraser の MIT、YOEO の Apache-2.0 は
> **リポジトリと追加重みに対するもの**であって、基盤の SD1.5 は
> CreativeML OpenRAIL-M（用途制限つき・商用可）である。RORem の基盤 SDXL は
> OpenRAIL++-M。個人利用は全て問題ないが、ShadeWave に載せる際は
> **基盤モデルのライセンスが実効的な制約**になる。ObjectClear と FLUX.1-Fill-dev は
> 非商用条項があるため候補から外す。

**読み取り**

1. **除去専用に学習されたモデルは LaMa に明確に勝つ。** 汎用インペインティング
   (PowerPaint) は勝てていない。タスク特化データの有無が決定的。
2. **SD1.5 系 (860M UNet) で足りる。** SDXL でなくても LaMa を上回れる。
   これは M1 16GB にとって決定的に重要（**実測: 重み fp16 1.80GB、実行時ピーク 5.4GB**）。

   > **実測レビューによる注意 (2026-08-24)**: この「SD1.5 で足りる」は、
   > **第3候補の RORem には当てはまらない**。RORem は SDXL ベース（2.567B、
   > **実測 fp16 4.90GB**）で、512² 運用なら 4 step 8.4 秒で成立するが、
   > **SDXL 本来の 1024² 運用は 4 step 27 秒・ピーク 7.6GB で不成立**。
   > Apache-2.0 という利点と M1 適合性はトレードオフの関係にある。
3. **few-step 蒸留が標準になった。** YOEO は 2 ステップ、RORem-4S は 4 ステップ。
   M1 でも実用速度に入る。
4. **ライセンスの選別が必要。** ObjectClear と FLUX.1-Fill-dev は非商用。
   RORem は Apache-2.0 で最も安全。

### 2.1 評価指標についての重要な知見 — PROVE ベンチマーク (2026)

PROVE (Perceptual RemOVal cohErence Benchmark) が、**v1 が踏んだ罠を正確に名指ししている**。

- 全参照指標 (PSNR/SSIM/LPIPS) は **「周囲からのコピー貼り付け」を高く評価する**
- 無参照指標は **「ぼけているほど綺麗」と誤判定する (Blur is Clean バイアス)**
- 提案指標 **RC-S**: DINOv2 特徴を穴の内側と周囲でスライディング窓で取り、
  **MMD で分布距離**を測る。正解画像が不要。人手順位との Spearman 相関 0.66〜0.82

v1 の評価は「合成マスク + 正解画像 + PSNR/LPIPS」だった。これは PROVE が
**構造的に人間と合わない**と結論づけた組み合わせそのものである。v2 では指標を入れ替える (§6)。

## 3. 対象の大きさ — **未知である**（初稿の「決定的な観測」は誤りだった）

> **反証レビューによる撤回 (2026-08-24)**
> 初稿はここに「対象は中央値 78×62px なので 512² クロップで足りる」と書き、
> それを設計の土台にしていた。**この数値は観測ではなく、合成マスクの定数の言い換えだった。**
> SPEC §17 が型 E として記録している「評価データの素性を確認していなかった」の再発である。

### 3.1 何が間違っていたか（検証済み）

| 主張 | 実際 |
|---|---|
| 「MobileSAM で抽出した実人物輪郭」 | `data/masks_dict.py:80` の `keep()` は**面積・充填率・境界接触しか見ていない**。人物クラスの判定は無い。`SamAutomaticMaskGenerator` の全セグメントが対象 |
| 「マスク外接矩形 中央値 78×62px」 | `data/masks.py:200` がシルエットを **`logU(0.12, 0.40)` × キャンバス**で拡縮している。512² なら長辺 61〜205px、幾何平均 112px。**測っていたのはこの定数である** |
| 「面積 中央値 1.0%」 | `data/masks.py:35` の `AREA_LO, AREA_HI = 0.001, 0.08` の対数一様。幾何平均 0.894%。実測値 0.95% はその再現 |

さらに、辞書 638 枚の外接矩形の縦横比を実測した:

```
h/w:  p10 0.37 / p25 0.60 / p50 0.96 / p75 1.56 / p90 2.84
  h/w > 1.8（立ち姿の人物らしい）: 131枚 = 20.5%
  0.8 < h/w < 1.25（ほぼ正方形）:  166枚 = 26.0%
```

立位人物の外接矩形は通常 2.5〜3.5:1 である。**中央値が 0.96（正方形）ということは、
辞書の大半が人物ではなく岩・葉・地面のパッチである。**

加えて 3 つのフィルタが大きい対象を構造的に排除している:
`AREA_HI = 0.08`（面積 8% 上限）、`MIN_FILL = 0.35`（腕脚のある人物を落とす）、
`MAX_BORDER = 0.35`（**タイル端で切れた大きい人物を落とす**）。
つまり「大きい人物は辞書に入れない」と決めた上で「対象は小さい」と結論していた。

### 3.1.5 実測で埋めた (2026-08-25) ★§3.2 の「未知」は解消済み

外部ストレージ再接続により §3.3 の M1 を実施した。実写真 250 枚 (人が写り込みやすい
93 ショットから無作為抽出) を現像し、**シーン全体を検出器に見せて** 210 件を測定。
**縦横比の中央値 2.54** で、立ち姿の人物 (2.5〜3.5) と一致する = 本物を測れている。

| | p10 | 中央値 | p90 | 最大 |
|---|---|---|---|---|
| 高さ | 106 | **250** | 751 | 5057 px |
| 幅 | 47 | **100** | 392 | 6268 px |

**大きさ別に見た 512² クロップの適用可否**

| 画面高さ比 | 件数 | 高さ中央値 | 512² に収まる |
|---|---|---|---|
| 〜5% (遠景の通行人) | 84 | 141px | **100%** |
| 5〜15% (中景) | 84 | 318px | 68% |
| 15〜40% (近景) | 32 | 710px | 0% |
| 40%〜 (主被写体) | 10 | 3229px | 0% |
| 全体 | 210 | 250px | **67.1%** (1024² なら 90.5%) |

**そして実行コストの制約と衝突している** (YOEO の実測):
**512² だけが実用点。** 768² は 6 倍遅くスワップし、1024² は fp32/fp16 とも
メモリで不可 (潜在 128²=16,384 トークンの注意行列が 8.6GB で MPS の上限超え)。
fp16+注意分割なら 1024² が 30 秒で動くが、**出力が NaN になる**ので使えない。

**したがって:**

1. **主用途「小さい人」(画面高さ 5% 以下、中央値 141px) は 512² で 100% 覆える。**
   ここが Phase 0〜2 の対象であり、実行コストとも整合する
2. **中景以上 (33%) には L4 (フル解像度復元) が必要。任意ではない。**
   反証レビューの「最もリスクの高い部品を、最も弱い測定を根拠に後回しにしている」
   という指摘が、実測で裏づけられた
3. 撤回した初稿の「中央値 78×62px」は、実測 250×100px の **1/3** だった

### 3.2 (解消前の記述) 正しい扱い

**対象の実サイズ分布は未知である。** したがって:

1. 「512² クロップ 1 枚で完結する」は**仮説**であって前提ではない
2. L4（フル解像度復元）を「Phase 4・任意」に後回しにする根拠が無い。
   もし実分布が 3〜10 倍大きければ、縮小 → 拡散 → VAE 往復 → 拡大が**主経路**になり、
   そこは v1 が肉眼で負けた「ぼけた塊」が戻ってくる場所である
3. 1億画素対応が「切り出し問題に還元できる」かどうかも、この測定に依存する

### 3.3 これを解消する測定（Phase 0 の必須項目・1日以内）

**M1. 実写真での実測（本命）**
実際に消したい写真を **30〜50 枚**選び、対象の実 px サイズを直接測る。
`/Volumes/PHOTOS 01` の再接続が必要（**読み出しのみ**）。ユーザの関与が要る唯一の作業。

**M2. shard からの自動測定（補助・オフラインで可能）**
既存 265,000 タイルから無作為に数千枚を抽出し、SAM3 の**テキスト条件付き**セグメンテーション
（`models--facebook--sam3` は tokenizer を持つ = "person" で条件付けできる）で人物を検出し、
外接矩形サイズと**タイル端に接する割合**を測る。端に接する率が高ければ、
「タイルより大きい人物」が相当数あることの証拠になる。

**M3. マスク辞書の作り直し**
`AREA_HI` / `MIN_FILL` / `MAX_BORDER` を外し、SAM3 で人物クラスに限定した辞書を作る。
これを行うまで、人物ベンチの結果は「人物」の結果として報告しない。

```
     │      ハルシネーション 0、ぼけ 0、粒状も本物                   │
     │                                                             │
     │  [A] 教師経路: 学習済み除去拡散モデル（512², 2〜4 step）      │
     │      + マスク膨張 + SmartEraser 式「物体を消さずに入力」      │
     │      + best-of-N & RORem 判別器による自動採否                │
     │                                                             │
     │  [B] 生徒経路: 教師から蒸留した小型 CNN（Core ML, 決定的）    │
     └────────────────────────────────────────────────────────────┘
                                  ↓
                 ┌───────────────────────────────────────────┐
                 │  L4  フル解像度復元（大きい対象のときだけ） │
                 │   ・構造は L3 出力、テクスチャは実画素      │
                 └───────────────────────────────────────────┘
                                  ↓
                 ┌───────────────────────────────────────────┐
                 │  L5  写真としての整合（自作・v1 資産を再利用）│
                 │   ・逆トーンマップ → リニア ProPhoto        │
                 │   ・周囲の実測から粒状注入（X-Trans 対応）   │

                                  ↓
                 ┌───────────────────────────────────────────┐
                 │  L6  自動検品                               │
                 │   ・SAM3 で穴の内側に新規物体が出ていないか │
                 │   ・RC-S が閾値を超えたら別シードで再試行   │
                 │   ・N 回失敗したら LaMa 出力に退避          │
                 └───────────────────────────────────────────┘
```

### 4.0 L2 HDR 変換の要件（実測で確定・自己レビューで追加）

既存 shard のタイル 24 枚を、v1 が使っている知覚空間
`p = sign(x)·(|x|/white)^(1/2.2)` (white = 99.5 パーセンタイル) で実測した。

| 量 | 中央値 | 最小 | 最大 |
|---|---|---|---|
| タイル内最小値 | +0.101 | **−0.219** | +0.511 |
| タイル内中央値 | +0.573 | +0.208 | +0.947 |
| 99.5 パーセンタイル | +1.138 | +0.756 | +1.224 |
| タイル内最大値 | +1.340 | +0.817 | **+1.696** |
| **1.0 を超える画素の割合** | **3.5%** | 0.0% | **27.5%** |
| 負の画素の割合 | 0.0% | 0.0% | 0.2% |

**含意**

1. **単純な `clip(0,1)` は不可**。中央値で 3.5%、最悪 27.5% の画素が飽和する。
   空や水面の輝きが白く潰れた画像を拡散モデルに見せることになり、
   モデルは「白潰れした空」に合わせた背景を作ってしまう。
2. **負値がある**（最小 −0.219）。ProPhoto→sRGB の色域変換でさらに増える。
   符号を保持する変換が必要。
3. したがって L2 は **軟らかい膝を持つ可逆トーンカーブ**でなければならない。
   例: `y = x` (x < k)、`y = k + (1-k)·tanh((x-k)/(1-k))` (x ≥ k)、k = 0.8。
   逆関数は `atanh` で厳密に求まる。負側は符号対称に適用する。
4. **マスク外は最終的に原画素で上書きする**ので、トーンカーブの誤差が
   写真に残ることはない。誤差が効くのは「モデルが何を見るか」だけである。

この測定は v1 の LaMa 評価では表面化しなかった。LaMa には
タイルごとに [0,1] へ線形正規化して渡していたためで、
線形正規化は**コントラストを変えてしまう**（拡散モデルでは分布ズレとして効く）。
v2 では膝つきトーンカーブに統一する。

### 4.1 L3 [A] 教師経路の詳細

**入力表現 — SmartEraser 方式を採る**

従来: `[mask, image ⊙ (1-mask)]`（穴を黒で潰して渡す）
本設計: `[mask, image]`（**物体を残したまま渡す**）

SmartEraser の測定によれば、これにより
①モデルが「何を消すのか」を正確に把握でき、対象を再生成する事故が減る
②穴の周囲の文脈をそのまま持ち込みやすくなる。
FID 21.23 → 10.90 の改善の主因がこれである。採用する。

**マスクの扱い**

- 学習時のマスクは正確、実運用のマスクは雑という乖離がある。
  SmartEraser の対策（膨張・凸包・楕円・外接矩形・ベジエ化の 6 変種で拡張）を
  推論側でも活かし、**入力マスクを常に数 px 膨張**させる（影・輪郭のにじみを含める）。
- SAM3 が既に環境にある (`~/.cache/huggingface/hub/models--facebook--sam3`) ので、
  クリックからのマスク生成に使える。

**サンプリング**

- 2〜4 ステップ (LCM / few-step 蒸留)。**実測 4.7〜11.0 秒/箇所**（冷機・N=1・CFGなし、§13）。
- シード固定 → **決定性を維持**（SPEC §9.1 の要求）。
- best-of-N: N=2〜4 で生成し、**RORem-Discriminator**（人手フィードバックで学習された
  採否判別器、Apache-2.0 で公開済）で最良を選ぶ。

> **反証レビューによる修正 (2026-08-24)**: 初稿は「best-of-N を蒸留データの選別にも
> 同じ仕組みで使える」と書いたが、**これは §4.2 の中核主張と矛盾する**。
> best-of-N を使った瞬間に Y は X の関数でなくなる（どの seed が選ばれるかが
> X と N 個の乱数に依存する）ので、「p(Y|X) がデルタ関数」という前提が崩れる。
>
> **切り分け**: best-of-N は **運用時の教師経路 [A] でだけ使う**（品質優先）。
> **蒸留データ生成では使わない** — 単一 seed 固定、`seed = hash(X, M)` とする。
> 判別器は蒸留データでは「選別」ではなく「破棄」にのみ使う。

> **実測レビューによる注意 (2026-08-24)**: best-of-N は**コストが線形に増える**。
> 実測（§13）では **N=1 で 6.85 秒、best-of-4 で 24.9 秒**（冷機）、
> 連続運転なら **34 秒**、CFG も付ければ **57 秒**。対話用途では成立しない。
> **既定は N=1、最大でも N=2** とし、N=4 は「うまくいかなかったときだけ手動で」に留める。
> 蒸留データ生成で best-of-4 を使うと総所要が 4〜7 日 → **14〜24 日**になり不成立。
>
> **設計上の解決**: 「常に N 枚生成して最良を選ぶ」のではなく、
> **§4.5 の検品に落ちたときだけ引き直す**（retry-on-failure）。
> 期待コストは `1 + 不合格率 × 追加回数` なので、不合格率 2 割なら平均 1.2〜1.4 枚で済む。
> 常時 best-of-4（= 4 枚）とは 3 倍以上違う。**こちらを既定とする。**

### 4.2 L3 [B] 生徒経路（自作モデル）の詳細

**なぜ作るか**

1. ShadeWave への組み込み。既存の `nagi_denoise` は Core ML `.mlpackage` で配布されており、
   同じ経路に載せられる（拡散モデルを Core ML に載せるより桁違いに簡単）。
2. 速度。512² で 50ms 以下。教師の 6〜15 秒とは実用感が違う。
3. 完全な決定性と、自前データ（X-Trans の粒状・色）への特化。
4. ライセンス的にも、配布物が自前の重みになる（ただし §8 の注意あり）。

**データ生成（自前写真のみ）**

> **自己レビューによる修正 (2026-08-24)**: 初稿では SmartEraser に倣って
> 「人物を貼り付けた合成入力」を作る計画だった。これは誤り。
> SmartEraser が貼り付け合成をするのは **正解画像 (元の背景) が必要だから**である。
> 蒸留では目標が教師出力なので **正解画像を必要としない**。したがって
> **実写のまま・実物体のまま・実マスクのまま**学習データを作れる。
> 貼り付け合成は「影が無い・被写界深度が合わない・光の回り込みが無い」という
> 分布のズレを持ち込むだけで、蒸留には一切利点がない。**合成はしない。**

```
既存資産: 265 shard × 1000 タイル = 約 265,000 枚の 512² 原寸タイル（実写・原寸）
          + SAM3 による物体マスク

for 各サンプル:
    実タイル X を選ぶ                                   ← 実写そのまま
    X の中の実在物体（人・鳥・標識・ゴミ等）を SAM3 で検出し 1 つ選ぶ
    マスク M = その輪郭を膨張 + 形状を変形（6 変種のいずれか）
    教師出力 Y = Teacher(X, M, seed固定)                ← 一意
    判別器スコア・SAM3 検品が閾値未満なら破棄
    保存: (X, M, Y)
```

利点:
- 入力が実写のまま。影も被写界深度も本物（貼り付け合成より遥かに近い）
- 正解画像を用意する必要がない → データ生成が単純になり、破棄率も下がる
- 物体が写っているタイルが足りなければ、マスクを「物体でない領域」に置いてもよい
  （教師はそこでも妥当な背景を作る。生徒はそれを真似ればよい）

> **反証レビューによる修正 (2026-08-24)**: 初稿は「**入力分布 = 実運用分布。
> ドメインギャップがゼロ**」と書いたが、**これは成立しない**。
> `data/extract.py:61` は `MIN_TILE_STD = 0.010` で「空や無地の壁を落とす」とし、
> `:62` は `MAX_TILE_SAT = 0.25` でハイライト主体のタイルも落としている。
> **実運用で小さな人物を消す背景は、空・無地の壁・アスファルト・水面が大きな比率を占める。**
> 生徒はそれらを一度も見ずに学習し、運用でそこに投入されることになる。
>
> **対処**: 蒸留データ専用に、`MIN_TILE_STD` / `MAX_TILE_SAT` を緩めた
> 補助タイル集合を切り出す。平坦背景を意図的に含める。
>
> 同じフィルタは §4.0 の HDR 実測にも効いている。「1.0 を超える画素 27.5%」は
> **既に飽和タイルを除外した母集団での最悪値**であり、実際の空の写真ではこれより悪い。
> §4.0 の結論（clip 不可）は強まるだけなので方向は正しいが、数値は楽観側である。

> **原理の要点**: 目標は「元の背景」ではなく「教師の出力 Y」である。
> 元の背景を目標にすると **v1 と同じ平均値回帰に戻る**（背景は入力から復元不能なので
> 条件付き分布が広がる）。Y を目標にすれば分布はデルタ関数になり、L1 で学習してよい。
> ここを取り違えると設計が崩壊する。

**この論理の弱点（自己レビューで発見・要対処）**

「p(Y|X) がデルタ関数だから L1 でぼけない」は**目標側については厳密に正しい**が、
**生徒側には抜け穴がある**。

生徒の容量が有限で、教師 T が入力に対して滑らかでない場合、
生徒は「近傍の X たちに対する T の平均」を出す。これは**入力空間での平均化**であり、
結果として再びぼける。拡散サンプラは入力の微小変化で別のモードに飛ぶことが知られており、
T の非滑らかさは現実の懸念である。

対策（優先順）:
1. **ステップ数の少ない教師を選ぶ** — 2〜4 step の蒸留済みモデルは、
   多ステップのサンプラより入力に対して滑らかである（軌跡が短いほど分岐が少ない）
2. **ノイズ入力を全サンプルで固定** — T の確率的自由度を消す
3. **判別器で採択したサンプルだけを使う** — T を「良い出力」の側へ均す効果がある
4. **生徒の容量を上げる** — 8M で足りなければ 20〜30M まで（Core ML なら許容範囲）
5. **最後の手段**: 蒸留で初期化した後に、**軽い敵対的損失で微調整**する。
   v1 の GAN 失敗（2回）はゼロから学習したためであり、
   良い初期値からの微調整は安定性が桁違いに高い。ゼロからの GAN とは別物として扱う。

対策 5 まで行っても駄目なら、生徒は諦めて教師をそのまま使う（Phase 3 は任意）。

**さらに 2 つの平均化機構（反証レビューで発見）**

**(c) 最適化側の平均化。** L1 の最適解が鮮鋭でも、有限ステップの SGD がそこへ到達する
保証はない。スペクトルバイアスにより高周波は最後に学習される。**v1 の実測がこれを示している**:
Stage G 第3版で grain は step 4500 で頭打ち、9,000 step まで回しても
「粒は粒のまま、構造にならなかった」。そして §4.2 は**その grain 0.176 を出した当の
Stage F (base96, 8.0M) をそのまま流用する**と書いている。
目標を差し替えれば同じ網が別物になる、という賭けである。

**(d) 破棄による共変量シフト。** 生徒は「教師が成功した X」だけで学習し、
運用では全 X を渡される。教師が失敗する 30〜40% の入力に対して生徒は無拘束になる。
「教師の 80〜95%」という見積りは**検品後の教師**を指しており、
生徒が学習するのは**検品前の単一 seed 出力**である。上限の見積りが 1 段高すぎる。

### 4.2.1 蒸留の前に必ず通すゲート（Phase 0b）— 反証レビューで追加

上記 (c) は、**教師データを 1 枚も作らずに検証できる**。

> **LaMa は既に手元にあり（`models/big-lama.pt`）、完全に決定的な教師である。**

したがって:

1. LaMa の出力を目標に、8.0M の Stage F を数千枚で蒸留する（データ生成コスト **0 日**）
2. 生徒の grain が LaMa の **0.875** に届くか、それとも v1 と同じ **0.2 付近**へ落ちるかを測る

**届かないなら、拡散教師でも同じ結果になる。** 4〜7 日のデータ生成を始める前に、
設計の中核主張を 1 日で反証できる。SPEC §17 の R13/R14（高価な実行の前に効くことを確認する）
の要求そのものである。

**併せて測る: 教師 T の非滑らかさ**

1. **マスク摂動感度**: 同一 seed で M を ±1px 平行移動・1px 膨張・境界ジッタさせ、
   穴の内側で `d(Y, Y')` を測る。これを**同一 M で seed だけ変えたときの距離
   `d(Y_s1, Y_s2)`（＝モード間距離）と比較する**。
   前者が後者に匹敵するなら、T は「確率的であるのと同程度に非滑らか」であり、
   決定的化は何も買っていないことになる。
   距離は `eval/perceptual.py` と `grain_ratio` / `psd_distance`（R12 準拠で陰性対照済）で測る。
2. **暗記能力の分離**: 200 組で意図的に過学習させ、train 上で Y を鮮鋭に再現できるかを見る。
   再現できて val でぼけるなら、それが「入力空間での平均化」の実測量である。

**規模とコスト**

| 項目 | 値 |
|---|---|
| 目標サンプル数 | 20,000〜30,000（採用後）。**公開データ解禁により Syn4Removal / RORD で増補可能**（§4.7-3） |
| 生成速度 | 8〜15 秒/枚（M1 Air、2〜4 step、判別器込み） |
| 破棄率見込み | 30〜40% |
| 総生成時間 | **約 4〜7 日**（連続実行。ファンレスなので放熱管理が必要） |
| 保存量 | **実測 2.142 MB/組 → 41.8〜62.7GB**（空き 118〜123GB）。ただし下記の最適化で 0.6GB まで落とせる |

> **実測レビューによる最適化 (2026-08-24)**: 保存量は 3 通りある。
> | 方式 | 1組 | 30,000組 |
> |---|---|---|
> | (X, M, Y) 素朴保存 | 2.142 MB | 62.7 GB |
> | (X, M, **Y−X 差分**) | 1.088 MB | 31.9 GB |
> | (**X は shard 参照**, M, Y−X 差分) | **約 21 KB** | **0.6 GB** |
>
> マスク面積が数 % なので Y−X 差分はほぼ空になる（実測 21.0 KB）。
> X は `shards/` に既にあるので shard ID + タイル index で参照すればよい。
> 学習時の読み直しコストは SPEC §10.1 P4 の実測（512² ランダムクロップ 2.59ms）から無視できる。
> **3 番目を既定とする。** ディスクの制約が事実上消える。

**モデル**

- 入力 7ch: RGB（物体が見えたまま）3 + マスク 1 + 低周波ガイド 3（任意）
- 本体: v1 の Stage F（FFC U-Net, base96, 8.0M params）をそのまま流用可能。
  InstanceNorm、BatchNorm 禁止（v1 で確認済みの制約）。
- 損失: **L1 + 知覚損失のみ**。GAN は使わない（目標が一意なので不要）。
- 学習: M1 で 30k step ≈ 1〜2 日（v1 実績）。
- 出力: Core ML 変換 → ShadeWave 組み込み。

**期待される到達点**: 教師の品質を上限として、その 80〜95% を再現。
教師が LaMa に明確に勝っていれば、生徒も勝つ余地が十分ある。

### 4.3 L5 写真としての整合 — v1 資産が活きる唯一の場所

拡散モデルの出力は「綺麗すぎる」。写真に貼ると、そこだけノイズが無く、
色がわずかにずれ、粒状が合わない。v1 で作った以下がそのまま使える。

| v1 資産 | 用途 | v1 での測定 |
|---|---|---|
| 粒状注入 (Stage D) | 穴の内側に周囲と同じ粒状を注入 | LaMa の grain 0.921 → 1.014 |
| `grain_ratio` / `psd_distance` | 粒状の整合度を測る | 陰性対照テスト済 |
| `photometric_align` | 局所の色・輝度統計を合わせる | 実装済 |
| `adaptive_blend(d0=4,d1=16)` | 縁からの距離に応じた合成 | 掃引済の最良値 |
| Poisson 合成 | 境界の段差解消 | **LaMa 出力には効果ゼロ**（拡散出力でも同様と予想） |

Poisson は既に無効と実測済みなので、**既定では使わない**。

### 4.4 参照フレーム経路 — 発想は有効。ただし既存の 2,220 組は使えない

**着想**: 通行人が動いた前後のカットがあれば、消したい人物の背後の真の背景が
別フレームに実際に写っている。位置合わせして実画素をコピーすればよい。
ハルシネーション 0、ぼけ 0、粒状も色も本物 — **どの生成モデルにも負けない**。

> **反証レビューによる撤回 (2026-08-24)**
> 初稿は `cache/pairs.jsonl` の 2,220 組を「既に発掘済みの資産」として扱った。
> **この 2,220 組は主用途の対象を原理的に含まない。**

**検証結果**

`data/pairs.py:65` の判別器は **16×16 の輝度サムネイル**で動き、
採択下限は `CELLS_LO = 0.01`（`:69`）＝ 256 セル中 **3 セル以上**の変化。

| | 値 |
|---|---|
| 実測 `diff_cells` の p10 | 3.0 セル = フレームの **1.17%** |
| 実測 `diff_cells` の中央値 | 8.0 セル = フレームの **3.12%** |
| 消したい対象（仮に 78×62px、6000×4000 中） | **0.052 セル = 0.020%** |

**検出下限が対象の約 60 倍。** これらは「小さい通行人が動いた」ペアではなく
「大きい何かが変わった」ペアである。

さらに `data/pairs.py:174` は `corr > 0.98 かつ diff_cells < 0.01` を近重複として
**除外している**。連写で人だけがわずかに動いたコマ — 露出も光線も一致する、
参照経路にとって最良の素材 — がまさにこの条件に該当する。
**欲しいものを能動的に捨てていた。**

その他の実測:
- 105 ショットしかなく、**単一ショット（2019-06-24 Budapest）だけで 1,076組 = 48.5%**。
  有効標本数は 2,220 ではなく実質 100 シーン程度
- `bg_corr` の **26.4% が 1.0 を超える**（`data/pairs.py:141` が部分集合上で
  再正規化していないため）。`MIN_BG_CORR = 0.97` は較正されていない量への閾値
- 偽陽性率が一度も測られていない。`data/pairs.py:39-45` には v1 の失敗
  （上位8組すべて使い物にならず）が記録され、`:253` は「目視確認が必須」と明記している

**正しい扱い**

発想は有効なので捨てない。ただし**判別器を作り直す必要がある**:

1. サムネイル解像度を 16×16 から **128×128 以上**へ（対象 0.02% を捉えるには最低限）
2. **近重複の除外をやめる** — そこが最良の素材である
3. 位置合わせ（ホモグラフィ + 局所フロー）と露出合わせを先に実装し、
   **合わせた後の残差**で判定する（サムネイル差分では露出変化と被写体移動が分離できない）
4. **偽陽性率を目視で測ってから**使う

優先度は **Phase 4 相当（任意）**に下げる。Phase 0〜2 の成否には関わらない。

**評価データとしての利用にも制約がある**
- 学習データ混入: 105 ショットのほぼ全てが `cache/extract_manifest.jsonl`（学習 shard の由来）
  に含まれる。**外部の学習済みモデル（LaMa / SmartEraser 等）の評価には影響しない**が、
  自作の生徒モデル（Phase 3）の評価には使えない
- 元 RAW は `/Volumes/PHOTOS 01`（アンマウント済み）。再接続が必要（**読み出しのみ**）
- 同一現像設定で 2 枚を再現像する経路がまだ存在しない。露出合わせは
  現像パラメータの一致で解くべきで、出力画素の統計合わせでは足りない

### 4.5 L6 自動検品 — 「肉眼で勝つ」ための最後の砦

拡散モデルの最大のリスクは **穴の中に別の物体を作ってしまうこと**である
（YOEO が "sundries" と呼んで専用の損失で抑制している問題）。
1枚でもこれが起きると、肉眼評価では即座に敗北する。自動で弾く。

1. 出力クロップに SAM3 を掛け、マスク領域内に新規インスタンスが出ていれば不合格
2. RORem-Discriminator（**人手の除去品質判定で学習された**）のスコアが閾値未満なら不合格
3. 不合格なら別シードで再試行（最大 N 回）、それでも駄目なら **LaMa 出力に退避**

> **反証レビューによる修正 (2026-08-24)**: 初稿は判定 2 に RC-S を入れていた。**これは外す。**
> RC-S は「穴の内側と周囲の特徴分布の MMD」なので、**この量を最小化する出力は
> 定義上『周囲のテクスチャをそのまま写したもの』**である。
> 「RC-S が下がるまでシードを引き直す」と、**最も無難で最も情報の少ない標本が
> 系統的に選ばれる**（Goodhart）。しかも PROVE が示したのは
> 「**手法間の順位**」と人手順位の相関 0.66〜0.82 であって、
> **同一手法のシード間選択に使える妥当性は示されていない**。
>
> **RC-S は報告用の指標としてのみ使い、選別には一切使わない。**
> 再試行の判定は、ハルシネーション検出（SAM3）と、人手判定で学習された
> RORem-Discriminator に限る。

これにより **最悪ケースが LaMa と同等に固定される**。
盲検A/Bにおいて「大負けする外れ値」が消えることの価値は大きい。

> **副作用（統計への影響）**: LaMa 退避が発動したケースは出力が LaMa と**ビット一致**するため、
> 盲検A/Bでは必ず「同等」票になり、`eval/ab_compare.py:314` で分母から除外される。
> 退避率が 3 割なら、提示 50 件 → 判定 35 件となり検出力が 0.90 → 0.86 程度に落ちる。
> **提示件数は退避率を見込んで決めること**（§7）。

### 4.6 ShadeWave への配備経路（調査済み）

生徒モデル（Phase 3）が無くても配備できることを確認した。選択肢は3つある。

| 経路 | 内容 | 実績・前例 |
|---|---|---|
| **A. 生徒 → Core ML** | 8〜30M の CNN を `.mlpackage` 化 | 既に `nagi_denoise` が `nagi_v2_l_ft2_t768_fp16.mlpackage` で配布済。同じ経路 |
| **B. 教師 → Core ML** | 拡散モデルを Core ML 化 | Apple 系の DiffusionKit（Core ML + MLX、PyTorch→Core ML 変換 + Swift 推論）が存在。前例として **CoreMLaMa**（LaMa の Core ML 版、約200MB、iPhone 13 Pro で約2秒） |
| **C. 教師 → Python + torch-MPS** | 現状の pixi 環境のまま | 最も手間が少ない。ShadeWave が Python アプリなので現実的 |

**C で始めて、必要になったら A へ移行する**のが妥当。B は生徒が失敗した場合の保険。

なお **IOPaint**（LaMa・各種拡散モデルを MPS で動かすローカルツール）が
実装の参考になる。同種の統合が既に成立している事実自体が、
Phase 0〜1 の技術リスクが低いことの傍証である。

### 4.7 公開データ解禁で可能になること（2026-08-24 追記）

制約が外れたことで使えるようになった資産と、その用途。**重要度順**に並べる。

**(1) 結合の正しさを、自前写真で判断する前に検証できる ★最も価値が高い**

SmartEraser が **RORD-Val / DEFACTO-Val / Syn4Removal-Val**（各約 5k）を
GoogleDrive / BaiduDrive で公開している。

これを使うと、**「自前写真で勝てない」と「結合を間違えている」を分離できる**。
論文値（RORD-Val で FID 10.90 / PSNR 19.99）を再現できなければ、
問題はモデルではなく我々の配線である。

v1 では「指標が壊れていて失敗に気づけなかった」事故が 3 件記録されている
(SPEC §12.2)。**外部の既知の正解と突き合わせられる状態は、この種の事故に対する
初めての防御になる。** Phase 0 の最初の手順に組み込む。

**(2) 「物体の背後の真の画素」を持つ実データが手に入る**

**RORD**（BMVC 2022, `github.com/Forty-lock/RORD`）は、実写で
「物体あり / 物体なし」のペアと画素精度のマスクを持つ。

SPEC §9.1 は「合成マスク評価は実際の除去タスクと分布が異なる（実際に物がある場所は
その影・反射・被写界深度が周囲に及んでいる）」という弱点を明記し、§9.2 で擬似ペア発掘に
挑んで失敗していた（§4.4）。**その弱点が、自前で掘る必要なく解消する。**

ただし **裁定は依然として自前写真の盲検A/B**である（§6.1）。RORD は
「実物体の影・反射を含む条件で壊れないか」を測る**追加の関門**であって、合否ではない。

**(3) 生徒モデルの学習データ不足が解消する**

Syn4Removal の合成パイプライン（1M 三つ組の生成手順が公開）と RORD が使える。
初稿の懸念だった「20〜30k は控えめ」「破棄による共変量シフト」の両方に効く。

**設計上の役割分担を守ること**:
- **公開データ** → 除去そのものの汎用能力（8bit sRGB でよい）
- **自前写真** → X-Trans の粒状・色・HDR への適合（ここが差別化）

公開データで薄めすぎると、生徒を作る意味（自前データへの特化）が消える。
混合比は実験で決める。

**(4) 人物マスクの問題が部分的に解消する**

§3.1 で判明した「マスク辞書に人物クラス判定が無い」問題は、
公開のセグメンテーション注釈で実物体クラスのマスクが手に入るため緩和される。
**ただし §3.3 の M1（自前写真での対象実サイズ測定）は依然として必要**である。
公開データの対象サイズ分布は、ユーザの撮影スタイルを代表しない。

### 4.8 各段で既存モデルを使えるか — 監査（2026-08-24 追記）

> **ユーザの指摘**: 「既存のモデルをそのまま、またはパイプラインに組み込むことを
> していないようですが理由はありますか？」
>
> **監査した結果、指摘は当たっている。** L3（除去コア）は確かに既存モデルを
> そのまま組み込む設計になっているが、**L4・L5・Phase 3 の 3 箇所で、
> 既存の選択肢を調べずに「v1 の資産を流用する」「自作する」を既定にしていた。**
> これは v1 を生んだ習慣そのものである。

| 段 | 初稿の方針 | 既存の選択肢 | 判断 |
|---|---|---|---|
| L0 マスク | SAM3 | — | ✅ 既存を使用済み |
| L1 クロップ | 自作 | — | 自作でよい（数十行の幾何処理） |
| L2 HDR 変換 | 自作 | **存在しない** | ✅ 自作が必然。除去モデルは例外なく 8bit sRGB 前提 |
| **L3 除去コア** | **既存** | SmartEraser / YOEO / RORem | ⚠️ **候補を出し尽くした (2026-08-30)。YOEO+L5 が最良だが LaMa に決定的な差をつけられていない** |
| L4 フル解像度復元 | v1 の Stage B を流用 | **HD-Painter** (ICLR'25、インペインティング専用 SR、2K まで)／**Ultra-HR Patch Adapter** (4K+、軽量アダプタの2段構成)／**InverFill** (few-step 拡散向け1段反転) | ❌ **既存を先に試すべきだった** |
| L5 調和・粒状 | v1 の Stage D を流用 | 色・輝度: **Harmonizer**（フィルタ係数を回帰する軽量型）／**DCCF**／**MKL-Harmonizer**（最適輸送・エッジデバイス向け、2025）<br>粒状: **該当なし** | ⚠️ **色・輝度は既存を試すべき。粒状だけが未カバー** |
| L6 検品 | SAM3 + RORem 判別器 | — | ✅ 既存を使用済み |
| **Phase 3 生徒** | **自作蒸留** | **YOEO は既に 2-step 蒸留済み（実測 4.68 秒/箇所）**／RORem-4S／FlashClear | ❌ **既存の蒸留済みモデルで足りる可能性が高い** |

**結論: 自作が必然なのは L2（HDR）と L5 の粒状部分だけである。**
この 2 つは「リニア float32 HDR」と「X-Trans のセンサー粒状」という、
外部モデルが誰も扱っていない領域だから残る。それ以外は既存を先に試す。

**Phase 3 の位置づけを再度下げる。** 初稿では「速度と Core ML 組み込みのため」と
書いたが、**YOEO の 2-step が実測 4.68 秒**である以上、速度は既存で足りている可能性が高い。
生徒を自作する理由として残るのは以下 3 点だけで、いずれも**測定で必要性を示してから**着手する:

1. ShadeWave への Core ML 配布（既存の `nagi_denoise` と同じ経路にできる）
2. X-Trans の粒状・色への特化（L5 で足りるなら不要）
3. 完全な決定性（既存モデルもシード固定で決定的なので、実質的な差は小さい）

**統合の足場**: IOPaint（LaMa と各種拡散モデルを MPS で動かすローカルツール）が
既に同種の統合を成立させている。**自前で配線を書く前に、これを足場にできないかを見る。**

### 4.9 規律の追加 — R17

v1 の失敗 6 件は R1〜R6、繰り返した 4 件は R11〜R16 として成文化されている（SPEC §17）。
**本監査で見つかった習慣を R17 として追加する。**

> **R17 — 自作する前に、既存で代替できないことを測定で示す。**
>
> 各段について「既存モデル・既存実装が無いか」を先に調べ、
> **あるなら先に試し、それが足りないことを測定で示してから自作に進む**。
> 「v1 の資産があるから流用する」は理由にならない。
> v1 の資産は v1 の設計前提の下で作られており、前提が変われば最適でもない。

### 規律の追加 — R18〜R20 (Phase 0 の実施で判明、2026-08-25)

> **R18 — 外部モデルは、自前データで判断する前に「そのモデルの土俵」で結合を検証する。**
>
> YOEO ではこれを飛ばし、盲検A/Bで 25.6% (明確な負け) という結果を得た。
> その後に結合の欠陥が 2 つ見つかり、直したら 56.2% になった。
> **「モデルが合わない」と「実装が間違っている」は、検証しないと区別できない。**
> SmartEraser では本家の `visual_examples` (正解画像つき) で先に検証し、
> マスク内 PSNR +8.5〜11.4 dB を確認してから自前データへ進んだ。
> おかげで「最下位」を実力として読めた。

> **R19 — 引き分けは「どれも良い」と「全部ダメ」に分けて記録する。**
>
> `=` の一語は意味が正反対のものを混ぜる。混ぜると**伸びしろの所在が消える**。
> v1 でも同じ構図があった: 盲検A/Bの「同等」4 件は実は「両方悪い」であり、
> 分けていれば「LaMa の絶対品質もこの用途では高くない」に早く気づけた。

> **R20 — 絞り込みの基準は、必ず「片方に有利になっていないか」を数えて確かめる。**
>
> `max(bd_LaMa, bd_YOEO)` は対称に見えるが、YOEO の継ぎ目が系統的に強いため
> **「YOEO が最悪なケース」だけを集めた** (採用 24 件中 23 件)。
> 各手法の worst を半数ずつ取る方式でも偏りは消えなかった。
> 最終的に「両者の出力の差」という完全に対称な量に変更した。
> **選別を実装したら、必ず「どちらが何件選ばれたか」を出力すること。**

## 6. 評価設計（v1 から全面的に入れ替える）

PROVE の結論により、**全参照指標を主指標にすること自体が誤り**だった。

| 層 | 手段 | 位置づけ |
|---|---|---|
| **結合の検証** | **RORD-Val で論文値を再現できるか**（§4.7-1） | 合否ではなく**前提条件**。これを通るまで自前写真での判断に進まない |
| **裁定** | 盲検A/B（`eval/ab_compare.py`、実装済） | **合否はここだけで決める**。二項検定 + Wilson 区間 |
| **追加の関門** | **RORD**（実物体の背後の真の画素・影・反射つき） | 合成マスクでは測れない「実際に物がある場所」での挙動。合否ではない |
| **裁定データ** | ①合成マスク（**§3.3 の M3 で辞書を作り直してから**）②**実際の除去タスク**（正解画像なし、自前写真から不要人物を選ぶ） | ②が新規で最重要。①は辞書修正まで「人物」の結果として報告しない |
| **選別禁止** | **代理指標で候補を絞ってから人に見せることを禁じる** | v1 の敗因の構造そのもの（§6.1） |
| 報告指標 | **RC-S**: DINOv2 特徴 × 局所窓 × MMD（正解不要） | 新規実装。**報告のみ。選別・再試行の判定に使わない** |
| 検品指標 | ハルシネーション数（SAM3 で新規インスタンス検出） | 新規実装。YOEO の MSN 相当。**陰性対照必須**（下記） |
| 診断のみ | PSNR / grain / psd / boundary（既存） | **合否に使わない**。退行検出用 |
| 規律 | R11〜R16（SPEC §17）をそのまま継承 | quickval・陰性対照・preflight |

DINOv2 ViT-S/14 は 21M params・Apache-2.0 で、M1 での実行コストは無視できる。

### 6.1 代理指標で絞ってから人に見せてはならない

v1 は「簡易 LPIPS で 13% 劣位＝接近している」と判断し、人手では 0勝16敗だった。
**代理指標が人間の判断を代表しなかった**というのが敗因である。

初稿は「Phase 0 で RC-S により 3 候補を 1〜2 に絞ってから人手A/Bへ」と書いていたが、
これは**同じ構造**である。RC-S は PROVE で「手法間の順位」との相関 0.66〜0.82 が
示されているだけで、相関 0.66 は順位を 3 分の 1 程度取り違える強さでもある。

**修正**: 候補の絞り込みは **ユーザ本人が比較シート（10ケース程度）を目で見て行う**。
これは R16（数値だけで判断せず必ず結果画像を見る）に沿っており、
代理指標を挟むより速くて確実である。絞った後に 40 判定の盲検A/Bを行う。

### 6.2 新規指標には両方向の陰性対照を置く（R12）

**RC-S**
- ぼかした出力 → RC-S が悪化すること（Blur is Clean バイアスが無いこと）
- 周囲のコピー貼り付け → RC-S が**不当に良くならない**こと（これが最重要）
- 細いマスク・小さいマスクで `nan` を返さないこと（v1 の grain の盲点の再発防止）

**ハルシネーション検出（SAM3）— 初稿はここに対照を置いていなかった**
- **陽性方向**: 穴の中に人物を貼った合成出力を「新規インスタンスあり」と検出できるか
- **陰性方向**: 除去が成功している出力を誤検出しないか（偽陽性率）

これは L6 の第一関門であり、§4.5 が「1枚でも起きると即座に敗北する」と
最重要視している検出器そのものである。壊れた検出器を使った判断は無意味になる。

## 8. 判断が必要な事項（実装前にユーザ確認）

### 8-1. 公開データで学習された重みを使うことの是非 → **解決済み（2026-08-24）**

ユーザ判断: **「既存のモデルを使用する場合には、公開データセットも学習済みデータも使ってよい」**

SPEC §6.2 の「公開データセットを使わない」は、**自前データのみで自作モデルを
学習する場合の方針**として維持し、既存モデルの利用にはかからない。

これにより本設計の最大の未確定要素が消えた。可能になることは §4.7 に記す。

> **1点だけ解釈を明示しておく**: 「生徒モデル（Phase 3）を公開データでも学習してよいか」は
> 文面上は明示されていない。本設計は **使ってよいものとして進める** —
> 教師の知識自体が既に公開データ由来であり、生徒はその蒸留物なので、
> ここで線を引いても実質的な意味がないため。
> 違う意図であれば §4.7 の (3) だけを落とせばよく、他は影響を受けない。

### 8-2. ライセンス

| 個人利用 | 全候補で問題なし |
| ShadeWave への商用組み込み | RORem = Apache-2.0（ただし基盤の SDXL は OpenRAIL++-M で使用制限あり）。ObjectClear / FLUX.1-Fill-dev は**非商用のため使用不可** |
| 蒸留した生徒モデルの配布 | **法的に灰色**。教師出力から学習した重みの権利関係は判例が定まっていない。商用配布するなら要検討 |

### 8-3. 発熱

M1 Air はファンレス。**15分の連続負荷で実測した**（§13）:

```
   0- 120s : 6.808 s/iter      600- 720s : 8.684
 120- 240s : 7.092             720- 840s : 9.205
 240- 360s : 6.960             840- 960s : 9.393
 360- 480s : 7.657
最初の60秒 6.804 s → 最後の60秒 9.393 s   低下率 +38.1%
```

別プロセスでの独立確認: SD1.5 UNet 1 step が **1082ms（冷機）→ 1499ms（熱時）= 1.385倍**。
**15分時点でもまだ単調に悪化しており、下げ止まっていない。**

**規律: 冷機ベースの全見積りに ×1.4 を掛ける。** 長期連続なら 1.4〜1.6 倍を見込む
（初稿の「1.5〜2倍」は 2 倍側が悲観的すぎた）。
夜間分割実行（1〜2時間動かして 30 分冷やす）で平均係数を 1.15〜1.25 に抑えられる可能性はあるが、
総経過日数は延びる。

## 9. 本設計が成立しなかった場合の代替案

Phase 0 で不合格だった場合（＝学習済み除去モデルでも自分の写真では LaMa に勝てない場合）:

1. **問題は写真側にある**可能性が高い（高周波の多い自然風景、X-Trans の粒状）。
   その場合は「除去」ではなく「置換の自然さ」を狙う方向へ再定義する必要がある。
2. 細い対象（電線 +2.28 dB、ストローク +0.42 dB）では v1 が既に勝っている。
   用途を絞った実用ツールとして完成させるのが最も確実な価値。
3. 目標自体の再設定（「LaMa に勝つ」ではなく「LaMa + HDR/100MP 対応」を価値とする）。

## 13. M1 Air 実機での実測（2026-08-24）

実現可能性レビューによる測定。**diffusers を使わず SD1.5 UNet / VAE / SDXL UNet を
素の torch で再構成し、パラメータ数が実物と一致することで構成の同一性を担保**している。

```
UNet in4   859.5M  (SD1.5 実物と一致)      VAE enc+dec  83.65M (一致)
UNet in9   859.5M  (SD1.5-inpaint と一致)  SDXL UNet    2.567B (一致)
```

環境: MacBook Air M1 (8-core GPU) / 16GB / macOS 15.7 / torch 2.12.1 / MPS

### 13.1 速度

| 要素 | 実測（冷機） |
|---|---|
| SD1.5 UNet **1 step**（潜在 64²）fp16 | **1082 ms** |
| 同 fp32 | 1044 ms（**fp16 より速い**） |
| 同 fp16 batch=2（CFG 相当） | 2110 ms |
| VAE encode 512² fp16 | 840 ms |
| VAE decode 512² fp16 | 1676 ms |
| CLIP text encoder (123M) | 14.5 ms（1回・キャッシュ可） |
| DINOv2 ViT-S/14 @518²（RC-S 用） | 171 ms |
| 参考: LaMa（SPEC §10.1 既存実測） | 530 ms / 512²タイル |

> **fp16 に速度メリットは無い。** M1 の GPU は fp16 演算器を持たない。
> fp16 を選ぶ理由は「速度」ではなく「常駐メモリ半減」である。

**1箇所あたり合計** = VAEenc + N_step × UNet + VAEdec

| 構成 | 冷機 | 連続運転（×1.38） |
|---|---|---|
| 2 step, N=1, CFGなし | **4.68 s** | 6.5 s |
| 4 step, N=1, CFGなし | **6.85 s** | 9.5 s |
| 4 step, N=1, CFGあり | 10.96 s | 15.1 s |
| 4 step, best-of-4, CFGなし | 24.9 s | 34.4 s |
| 4 step, best-of-4, CFGあり | 41.3 s | **57.0 s** |

**ボトルネック**: 1 step 1056ms のうち **637ms（60%）が 320ch@64² の自己注意**
（4096トークン × 5ブロック）。M1 の生の演算力は十分（conv3x3 で 2.74〜2.91 TFLOPS 実測）で、
**SDPA がこの形状で効率を出せていない**ことが原因。

### 13.2 発見した高速化 2 件

**(a) SDPA をやめて手動 matmul にする — 本設計で自己検証済み**

```
4096tok × 8head × 40dim:
  fp16  F.scaled_dot_product_attention 116.66 ms  /  手動 46.97 ms  → 2.48倍
  fp32  同                             102.95 ms  /  手動 71.38 ms  → 1.44倍
```
UNet 全体で 1082 → 718 ms（約 1.5倍）。**Phase 0 で最初に試す。**

**(b) クロップを小さくする**

| 潜在 | 画像 | UNet 1 step | 4 step 合計 |
|---|---|---|---|
| 32² | 256² | 249 ms | **1.81 s** |
| 48² | 384² | 704 ms | — |
| 64² | 512² | 1198 ms | 8.06 s |
| 96² | 768² | 4932 ms | — |

256² は 512² の **4.5倍速い**。ただし SD1.5 は 512² 学習であり、
**§3 を撤回した以上「対象が小さいから 256² で足りる」とは今は言えない**。§3.3 の測定待ち。

### 13.3 メモリ

| 構成 | 重み | 実行時ピーク |
|---|---|---|
| SD1.5 UNet + VAE, fp16 | **1799 MB** | 4389 MB |
| 同 fp32 | 3598 MB | 5958 MB |
| + CLIP text + DINOv2, fp16 | **2002 MB** | **5437 MB** |
| 15分連続実行中 | — | **5419 MB で完全に安定**（リーク無し） |
| SDXL UNet のみ fp16 | **4897 MB** | 5422 MB (512²) / **7646 MB (1024²)** |

ピークの正体は **VAE decoder の 512² 中間活性**（512ch × 512² × fp16 = 268 MB/枚）。
tiled decode で削減可能。

**SAM3 は 3.2GB (fp32)。SD1.5 と同時常駐させると 9〜11GB ピークで危険域**
（SPEC §10.1 P3 に 11.9 s/step のスワップ前例あり）。**別プロセスに分離すること。**

### 13.4 ディスク

既存 shard の実タイル 12 枚で計測。詳細は §4.2 の表を参照。
shard 全体は 251.4 GiB / 265 shard × 1000 タイル、1タイル 1.026 MB（圧縮率 1.46倍）。

### 13.5 依存関係（`pixi lock` のみ、インストールなし）

**torch 2.12 ピンは守られる。** プロジェクト全依存 + diffusers/transformers/accelerate/peft で solve 成功:

```
torch 2.12.1 ✓ / numpy 2.4.6 ✓ / torchvision 0.27.1 ✓  （いずれも現行 env と同一）
diffusers 0.40.0 / transformers 5.15.1 / accelerate 1.14.0 / peft 0.20.0
```

**要注意**: 無制限だと transformers が **5.15.1** に上がる。diffusers 0.40.0 は
transformers 5.x を前提に作られていない可能性が高く、`CLIPTextModel` の API 変更で壊れうる。
**`transformers = ">=4.44,<5"` を明示ピンし、diffusers 0.39.0 + transformers 4.57.6 の
組み合わせを使うこと**（この組み合わせでも solve 成功を確認済み）。

`external/libraw_enhanced/_core.so` の numpy ABI は、現行 env が既に numpy 2.x なので影響なし。

### 13.6 MPS オペ

拡散モデル推論に必要な主要オペ（SDPA、GroupNorm、LayerNorm、SiLU、GELU、
ConvTranspose2d、Conv2d、Linear、matmul、softmax、embedding、cumprod 等）は
fp16/fp32 とも**すべて動作**。

**2 件の既知の制約は今も残っている（本設計で再確認済み）**:

```
F.interpolate(mode="area")  100→37 (非可分)  : FAIL
    RuntimeError: Adaptive pool MPS: input sizes must be divisible by output sizes
grid_sampler_2d_backward                      : FAIL (未実装)
```

- `interpolate(area)` は**出力サイズが入力サイズを割り切るときだけ**動く。
  SPEC の失敗記録は現在も有効であり、「解消済み」ではない
- `grid_sampler_2d_backward` の未実装は**拡散モデル推論には影響しない**（forward のみ使用）。
  §4.4 の参照フレーム経路も推論のみなので成立する。影響するのは
  「warp を勾配経路に入れて学習する」場合だけで、v2 設計にはそれが無い

FFC U-Net 用の `rfft2 + irfft2` の backward も動作を確認（生徒モデル用）。
